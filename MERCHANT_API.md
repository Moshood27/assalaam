The "Pay with Attaqwa" Merchant QR API

Overview
- Any member can act as a local merchant and receive wallet payments from other members via QR code.
- Flow: Merchant generates a QR payload → Customer scans it in the app → App resolves recipient → Customer confirms amount and enters PIN → Funds move P2P from customer wallet to merchant wallet.

QR Payload Format
- Scheme: attaqwa:pay
- Query parameters:
  - to_type: membership | phone
  - to: merchant identifier (membership number or phone number)
  - branch_id: optional integer (required if membership number is reused across branches and needs disambiguation)
  - amount: optional number (merchant-suggested amount; payer may override)
  - note: optional short description (<= 120 chars)
  - medium: always set to "qr" when generated by the API
- Example: attaqwa:pay?to_type=membership&to=ABJ-04521&branch_id=12&amount=3500&note=Groceries&medium=qr

Endpoints (Authenticated)
- GET /api/merchant/pay/qr
  - Purpose: Generate a QR payload the merchant can print or show.
  - Query/body params (optional):
    - to_type: membership|phone (defaults to membership; falls back to phone if the member has no membership_number)
    - amount: optional numeric minimum 1
    - note: optional <=120 chars
  - Response JSON:
    - payload: string (attaqwa:pay?...)
    - display.merchant: { id, name, membership_number, branch_id }
    - display.suggested_amount: number|null
    - display.note: string|null

- POST /api/merchant/pay/resolve
  - Body: { qr: string }
  - Parses and resolves the QR payload to a merchant/member.
  - Returns 422 if multiple members match by membership_number (includes branches list), or 404 if not found.
  - Success response JSON:
    - to_type, to, branch_id
    - recipient: { id, name, membership_number, branch_id, branch_name }
    - amount: number|null
    - note: string|null

- POST /api/merchant/pay
  - Body: { qr: string, pin: 4-digit string, amount?: number, note?: string, branch_id?: number }
  - Executes the payment from the authenticated payer to the merchant in the QR payload.
  - Amount precedence: explicit amount in request body overrides amount in the QR. If neither is present → 422.
  - This delegates to the existing /api/wallet/transfer logic for PIN verification, balance checks, and transaction recording.
  - Returns the standard wallet transfer response on success.

Security Notes
- For MVP, payloads are not signed. The payer always sees the resolved recipient details and must confirm before paying.
- The payer’s 4-digit transaction PIN is required for payment, and the existing transfer limits/logic apply.

Error Cases
- 422: Invalid QR payload, missing amount, multiple recipients (requires branch selection)
- 404: Recipient not found
- 403/409/422: As returned by /api/wallet/transfer (e.g., invalid PIN, insufficient balance)

Implementation Details
- Controller: App\\Http\\Controllers\\Api\\MerchantPayController
  - generateQr(), resolve(), pay()
- Routes: routes/api.php (under auth:sanctum, inactivity middleware)
  - GET /merchant/pay/qr
  - POST /merchant/pay/resolve
  - POST /merchant/pay
- Reuses existing WalletController::transfer() to ensure consistent behavior and ledger entries.

Future Enhancements
- Optional payload signing to prevent tampering.
- Static QR (no amount) vs dynamic QR (includes amount) templates in the mobile app.
- Merchant profiles and settlement reporting screens.
